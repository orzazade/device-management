# Review findings — 2026-08-24 (Opus team, 237 raw → deduped)

Working checklist. `[x]` = fixed + verified in UI + committed locally. NO push until user says so.

## Verdict

DeviceDesk is a genuinely well-built v1 — the CQRS-lite command layer, the Postgres exclusion constraint on bookings, in-transaction audit writes on every mutating handler, and the two-phase Excel import are better than most internal tools ever get. But "feature-complete and browser-verified" hides a class of defects that browser-clicking cannot reach: three privilege/lifecycle holes (a manager can mint an admin account via POST /users; AuthGuard reads role and active-ness from a 12h JWT it never re-checks, so deactivating or demoting anyone is a no-op until the token expires; the seed admin ships as admin123 with no rate limit and no forced change), a booking-engine hole where an overdue loan stops blocking the device because the constraint window ends at the original to_date, and two device-status paths that resurrect written-off hardware. One shipped UI bug is outright destructive: ConfirmModal's buttons default to type="submit" and it is rendered inside the device edit form, so clicking "Cancel" on the delete dialog silently saves the device and clicking "Delete" races a PATCH against the DELETE. Beyond correctness, the app is built for the tester and not for the staff who run the lab: there is no lab-wide view of who holds what or what is overdue, no return check-in a desk person can perform, no rejection reason, no password self-service, and the audit log never names which device or request a row is about. None of this needs a rewrite — the architecture is right and most fixes are localized. Budget roughly a week on the ten items below before putting ~100 people on it; the rest is real but survivable.

## All findings by theme

### Booking engine & data integrity

- [ ] **F1** [critical/bug] An overdue loan stops blocking the device — the constraint window ends at the original to_date
  - The exclusion constraint keys on daterange(from_date, to_date, '[]') for approved/active/overdue (migrations/1724800000000-requests.ts:24-27). scanOverdue only flips state; to_date stays in the past, so from the next day the overdue booking overlaps nothing current and Postgres accepts a new approved booking for a device that is physically out. The double-booking the constraint exists to prevent, on the most common real case.
  - fix: Maintain an effective_to that is to_date for approved and 'infinity' for active/overdue and exclude on that, or add a partial unique index on device_id WHERE state IN ('active','overdue').
  - area: apps/api/src/migrations/1724800000000-requests.ts
- [ ] **F2** [critical/bug] Auto-approve overlap rolls back the whole create — the tester's request vanishes with a 409
  - In busy_only mode the handler transitions the fresh request to approved and re-saves inside the same transaction (requests.commands.ts:94-110). A constraint hit throws overlapError, rolling back the insert too, so the tester gets an error and has nothing pending. The device.holderId === null guard also ignores approved future bookings entirely.
  - fix: Wrap the auto-approve in a SAVEPOINT, or pre-query for an overlapping approved/active/overdue booking and simply leave the request pending when one exists.
  - area: apps/api/src/requests/requests.commands.ts
- [ ] **F3** [high/bug] No row lock or version column — concurrent approve/cancel silently lose each other
  - loadRequest is a plain findOne with no FOR UPDATE and DeviceRequest has no @VersionColumn (requests.commands.ts:16-23). transition() validates the in-memory state, so a manager approving while the tester cancels both pass the check and both write; last commit wins with no conflict and two contradictory audit rows. Same hazard on the device row in ConfirmHandover.
  - fix: Add lock: { mode: 'pessimistic_write' } to loadRequest and the device fetches, or a @VersionColumn so TypeORM raises and the API returns 409.
  - area: apps/api/src/requests/requests.commands.ts
- [ ] **F4** [high/bug] Overdue scan writes a stale entity, clobbering a concurrent return
  - scanOverdue selects late requests outside any transaction then transitions the stale in-memory entity inside one (jobs.service.ts:64-93). A tester who returns the device between select and save has their 'returned' row overwritten with 'overdue' — they get chased for a phone they handed back. The boot-time queue.add on every replica lets two pods process the same row too.
  - fix: Re-read with a write lock inside the transaction, or make it one guarded UPDATE ... WHERE state='active' AND to_date < :today RETURNING id and drive notifications off the returned ids.
  - area: apps/api/src/jobs/jobs.service.ts
- [ ] **F5** [high/bug] Handover force-closes the previous holder's loan as a clean return, with no check-in and no notification
  - ConfirmHandoverHandler transitions every active/overdue request on the device to 'returned' as closed_by_handover (requests.commands.ts:246-263). No accessory check, no damage question, no repair row — the history claims the previous tester returned it clean. Nobody tells them their loan was closed. RepairsController.advance does the same as closed_by_repair.
  - fix: Refuse the handover with a 409 while an active/overdue loan exists ("check in the current loan first"), and give staff an explicit force-return that goes through the real check-in form. Notify the previous holder either way.
  - area: apps/api/src/requests/requests.commands.ts (agreement: 3)
- [ ] **F6** [high/gap] No overdue → active transition: extending a late loan leaves it overdue forever
  - REQUEST_TRANSITIONS.overdue = ['returned'] (device-request.entity.ts:22-30). OverrideTimeHandler explicitly allows changing dates on an overdue request but only touches the dates, so "they need it three more days" produces a request with a future due date still flagged overdue, still nagging, with no path back to active.
  - fix: Add overdue: ['returned','active'] and have OverrideTimeHandler transition back to active when the new toDate >= today, with an overdue_cleared audit row.
  - area: apps/api/src/entities/device-request.entity.ts
- [ ] **F7** [high/bug] Approve never re-checks that the device is still lendable
  - CreateRequestHandler blocks retired/in_repair devices (requests.commands.ts:55-57) but DecideRequestHandler re-checks nothing. A request made Monday for a phone that went into repair or was soft-deleted Tuesday can be approved Wednesday, and ConfirmHandover then sets status='assigned' on a retired or deleted device.
  - fix: Reload the device in DecideRequestHandler on approval and reject with 409 when retired, in repair or soft-deleted; repeat the guard in ConfirmHandoverHandler.
  - area: apps/api/src/requests/requests.commands.ts
- [ ] **F8** [high/gap] Approved-but-never-collected requests never expire and hold the device's calendar
  - 'approved' is inside the exclusion constraint's WHERE clause so it reserves the range, but scanOverdue only looks at state='active'. A booking approved and never picked up sits forever, keeps appearing in pending-handover, and keeps its dates reserved. Handovers offers only "Confirm handover" — no way out when the tester went on holiday, even though approved→cancelled is a legal transition.
  - fix: Add a stale-approval scan that flags or auto-cancels approved requests whose fromDate has passed, and a "Can't hand over" action on Handovers calling /requests/:id/cancel with a reason.
  - area: apps/api/src/jobs/jobs.service.ts (agreement: 2)
- [ ] **F9** [medium/gap] Handover has no date gate — any approved request can be activated on any day
  - ConfirmHandoverHandler checks who confirms but never compares fromDate to today (requests.commands.ts:228-282). A booking for next month can be handed over now (assigned for weeks with no overdue detection), and one whose window has passed can be handed over and is instantly overdue. CreateRequestHandler also never rejects a past fromDate, and pendingHandover lists every approved request regardless of date.
  - fix: Reject handover when today < fromDate (allowing a day's lead) or today > toDate, reject creation with a past fromDate, and filter pending-handover to bookings starting soon.
  - area: apps/api/src/requests/requests.commands.ts
- [ ] **F10** [medium/bug] @IsDateString accepts full timestamps, so ranges can shift a day and the from<=to guard can be fooled
  - CreateRequestDto and TimeDto validate with @IsDateString(), which accepts '2026-08-24T22:00:00.000Z'. The handlers compare as strings (requests.commands.ts:58, 190), so a mixed-format reversed range passes lexicographically, and Postgres casts the timestamp to a date in UTC, silently shifting an evening booking a day earlier for a UTC+4 user. Only chk_range catches the worst case, as a 500.
  - fix: Use @Matches(/^\d{4}-\d{2}-\d{2}$/) on all four date fields so only calendar dates reach the handlers.
  - area: apps/api/src/requests/requests.controller.ts
- [ ] **F11** [medium/ux] The overlap 409 does not say which booking conflicts
  - overlapError() returns a fixed string (requests.commands.ts:29-32). A manager approving from the queue gets "already has an approved booking that overlaps" with no dates, no holder, no link — and the request stays pending with no record of the failed attempt, so the next manager tries again.
  - fix: On 23P01, query the conflicting row and include its dates and requester in the message; write an approval_blocked audit row so the failure is visible on the request.
  - area: apps/api/src/requests/requests.commands.ts
- [ ] **F12** [medium/gap] The booking rule and every command handler are untested; 23P01 detection guesses at driver internals
  - request-machine.spec.ts drives REQUEST_TRANSITIONS against itself — it asserts the table matches the table. Nothing tests the exclusion constraint, the overlap-to-409 mapping, the handover force-close or the overdue scan. isOverlapError reaches into e.driverError.code; if TypeORM or pg changes that shape, overlaps become unhandled 500s with nothing to catch it.
  - fix: Add an integration suite against a throwaway Postgres covering: two overlapping approvals, overdue then new approval, handover with an existing active loan, and the busy_only conflict path.
  - area: apps/api/src/requests/request-machine.spec.ts (agreement: 2)
- [ ] **F13** [low/gap] No dedupe on duplicate pending requests, and on-behalf ids are unvalidated
  - Pending rows sit outside the exclusion constraint, so a double-clicked form creates two identical pending requests, and nothing stops a tester requesting a device they already hold — DeviceDetail happily offers "Request this device" in both cases. onBehalfOfId is passed straight to requesterId with no existence check, so a bad UUID surfaces as a foreign-key 500 and CreateRequestHandler's ?? 'someone' fallback masks a missing user.
  - fix: Reject a create when an identical pending request or an existing hold by the same requester exists; look up onBehalfOfId first and 400 when missing, soft-deleted or inactive. Drop the 'someone' fallback.
  - area: apps/api/src/requests/requests.commands.ts (agreement: 3)
- [ ] **F14** [low/improvement] GET /requests and pending-handover load everything with joins and filter in JS
  - list() has no limit, offset or date filter, so ?scope=all pulls every request ever made with three joins (requests.controller.ts:121-140). pendingHandover fetches every approved request and filters by holder in JavaScript (143-158). Survivable in week one, painful by month six, and it means the requests page can never page back through history.
  - fix: Add take/skip with a default of 50 and a total count; move the holder filter into the query builder.
  - area: apps/api/src/requests/requests.controller.ts (agreement: 2)

### Authorization & account lifecycle

- [ ] **F15** [critical/bug] A manager can create an Admin account and take it over
  - POST /users is @Roles('admin','manager') (users.controller.ts:165) and CreateUserDto.role is only @IsIn(ROLES) — no rank check. Role changes are correctly admin-only, so the intent is clear, but creation has no such guard and Users.tsx:310 offers managers the Admin option. A manager creates admin2@…, signs in, and has approval mode, the audit log, write-off and user deletion.
  - fix: Reject dto.role === 'admin' unless req.user.role === 'admin' (consider gating 'manager' too), and filter the role select in Users.tsx by the caller's rank so the option never appears.
  - area: apps/api/src/users/users.controller.ts (agreement: 2)
- [ ] **F16** [critical/bug] Deactivating, deleting or demoting a user has no effect for up to 12 hours
  - AuthGuard verifies the JWT and reads name/email/role from the claims, never touching the DB; /auth/me echoes the same claims; the token TTL is 12h (config.ts:11) with no revocation. The active:false check exists only at login (local-identity.provider.ts:14). An off-boarded tester keeps requesting and receiving devices; a demoted manager keeps the Manage sidebar and passes every @Roles check. The admin gets no signal it did not take effect.
  - fix: Load the user by sub in the guard (short Redis cache — Redis is already a dependency), reject on deletedAt or active === false, and take role from the DB row. Have /auth/me return the DB row so the shell picks up role changes.
  - area: apps/api/src/auth/auth.guard.ts (agreement: 3)
- [ ] **F17** [critical/bug] Seed admin ships as admin123, the override env var is undocumented, and nothing forces a change
  - The init migration inserts admin@devicedesk.local with SEED_ADMIN_PASSWORD ?? 'admin123' (1724600000000-users-audit.ts:34). env.example lists only PORT, DATABASE_URL and REDIS_URL — SEED_ADMIN_PASSWORD, JWT_SECRET and SMTP_URL are all missing, so an operator following the documented setup deploys the default. config.ts:18 fails the boot when JWT_SECRET is missing in production; there is no equivalent for the seed password. Combined with no login rate limit, a known account with a known password sits on the public ingress.
  - fix: Throw at boot in production when SEED_ADMIN_PASSWORD is unset (or generate and log one once), add all four vars to env.example, and add a mustChangePassword flag the login flow enforces.
  - area: apps/api/src/migrations/1724600000000-users-audit.ts (agreement: 2)
- [ ] **F18** [high/bug] The last admin can be demoted or deactivated — only delete is guarded
  - softDelete counts remaining admins and refuses to remove the last one (users.controller.ts:118-121), but ChangeUserRoleHandler and the active:false branch of UpdateUserHandler have no such check, and changeRole does not block changing your own role. One PATCH leaves the instance with zero admins: nobody can flip approval mode, write off a device, read the audit log or restore the role. Recovery needs hand-written SQL against production.
  - fix: Extract one 'would this leave zero active, non-deleted admins' helper and call it from delete, role change and deactivate; refuse on self.
  - area: apps/api/src/users/users.commands.ts (agreement: 2)
- [ ] **F19** [high/bug] A manager can rename an admin and change the email that is their login
  - PATCH /users/:id is open to managers and only gates active and newPassword (users.controller.ts:181-185). Nothing stops a manager targeting an admin. Login is by email (local-identity.provider.ts:13), so changing an admin's email locks them out with no self-service reset to recover with; renaming them also corrupts the audit trail, where actorName is a stored copy.
  - fix: Refuse the patch when the target's role outranks the caller, and treat email changes as admin-only like active and newPassword. Render Edit read-only for higher-ranked rows in Users.tsx.
  - area: apps/api/src/users/users.controller.ts (agreement: 2)
- [ ] **F20** [high/bug] Deactivate skips every guard delete enforces — devices stranded on an account that cannot sign in
  - softDelete refuses while the user holds devices or has open requests (users.controller.ts:122-131); UpdateUserHandler writes active=false with no checks (users.commands.ts:79-83). Deactivating is the natural move when someone leaves, and it leaves their three devices held by an account that can no longer log in to return them, plus pending requests nobody can resolve.
  - fix: Move the holder/open-request/last-admin checks into one shared guard used by delete, deactivate and role change. Deactivate should warn with counts ("Aysel still holds 3 devices — deactivate anyway?") and offer to hand them back.
  - area: apps/api/src/users/users.commands.ts (agreement: 2)
- [ ] **F21** [high/gap] Staff can approve their own device request
  - DecideRequestHandler stamps decidedById = actor.id without ever comparing the actor to requesterId or createdById (requests.commands.ts:128-168). A manager requests a phone and approves it with the next click, and the audit row is indistinguishable from a legitimate approval. GOALS.md states the launch policy as 'every request needs approval'; a self-approvable request is not approved.
  - fix: Reject when actor.id equals requesterId or createdById with a clear 409. If admins should be exempt, make that explicit and give the audit row a distinct self_approved action.
  - area: apps/api/src/requests/requests.commands.ts
- [ ] **F22** [high/gap] No rate limit or lockout on login, and unknown emails answer measurably faster
  - POST /auth/login is @Public() with no throttler anywhere — @nestjs/throttler is not a dependency and no Fastify plugin does it. Passwords can be guessed at wire speed against a known seeded account. LocalIdentityProvider.verify returns null immediately when no row matches and only runs bcrypt when one does, revealing which corporate addresses have accounts. Nothing logs repeated failures.
  - fix: Add a per-IP and per-email limit on /auth/login plus a temporary lockout after N failures; always run a bcrypt compare against a dummy hash on a miss; audit failed logins.

- [ ] **F23** [high/bug] Re-adding a soft-deleted user or reusing a deleted project name returns a raw 500
  - users.email is UNIQUE across all rows including soft-deleted ones, but CreateUserHandler checks duplicates with a findOne that TypeORM filters to non-deleted rows (users.commands.ts:22). The insert hits 23505 and, with no exception filter in apps/api/src, the client gets "Internal server error". projects.controller.ts:130 has the identical defect on Project.name, and restore hits it from the other side. CreateDeviceHandler already does this correctly with withDeleted plus a "restore it instead" message.

  - The user menu contains only Sign out (Layout.tsx:170-175); Login has no forgot link; passwords change only via PATCH /users/:id with newPassword, admin-gated (users.controller.ts:172-189). There is no /auth/change-password and no /profile route despite ROADMAP S1. Onboarding ~100 people means an admin inventing and knowing every credential and then handling every reset for the life of the tool.
  - fix: Add POST /auth/change-password (current + new) and a profile page for every role; put a "Forgot password? Ask an admin at <address>" line on the login card; force a change on admin-created accounts at first sign-in.

  - requests.controller.ts:107 passes dto.onBehalfOfId straight through with no validation, and CreateRequestHandler saves first then looks the name up with a ?? A deactivated or soft-deleted user can be made the requester and, after handover, the recorded holder of a physical phone nobody will chase — they get no email either, since notify filters deleted users.

### Repairs & device lifecycle

- [ ] **F33** [critical/bug] Write-off leaves the borrower's request open, and returning it un-retires the device
  - advance() to in_repair force-closes every active/overdue request (repairs.controller.ts:106-127), but writeOff() only sets status='retired' and holderId=null (159-162). Every toast is hard-coded to 4000ms regardless of kind, so long error text like a validation list scrolls past before it can be read, and there is no close button and no pause on hover. The stack is unbounded, so a bulk action pushes toasts up over the content, and they sit bottom-centre where modal footer buttons live.
  - fix: Wrap the container in role="status" aria-live="polite", give errors a longer or manual dismissal with an × button, pause the timer on hover, and cap the visible stack at 3.
  - area: apps/web/src/components/Toasts.tsx (agreement: 2)
- [ ] **F191** [medium/ux] Header search and the Devices page filter are two boxes that drift out of sync
  - The header form navigates to /devices?q=… and Devices mirrors ?q= into its own input, but the sync is one-way: typing in the page filter never updates the header box or the URL, so the user stares at two search fields showing different text with only one driving the table. The header box has no clear button, no submit affordance and no hint that Enter is required — it looks like a live filter and does nothing until Enter. There is no / or ⌘K shortcut.
  - fix: Make the Devices filter the single source of truth by writing to ?q= (debounced setSearchParams), have the header input read the current ?q= when on /devices, and add a clear button, a search icon, an aria-label and a "/" focus shortcut.
  - area: apps/web/src/components/Layout.tsx
- [ ] **F192** [medium/improvement] Badge counts pull two full request lists per user every 30 seconds
  - To render two small numbers, Layout runs /requests/pending-handover and /requests?scope=all&state=pending on a 30s interval, and Bell adds /notifications. Neither request endpoint paginates: pendingHandover loads every approved request with device+holder+requester joins and filters in JavaScript, and the staff pending query returns all rows joined three ways. With ~100 users that is roughly 600 fully-joined list queries per minute whose only consumer is two integers.
  - fix: Add a single GET /me/counts returning { pendingHandover, pendingApprovals, unreadNotifications } computed with SQL COUNTs, shared by Layout and Bell.
  - area: apps/web/src/components/Layout.tsx
- [ ] **F193** [medium/bug] Sign-in form flashes on every reload for already-signed-in users
  - Login only checks user and ignores loading from useAuth. On any hard refresh at /login — or any redirect there — user is null while /auth/me is in flight, so the full sign-in card renders and then jumps to the dashboard. On a slow corporate network that flash lasts long enough that people start typing their password into a form about to disappear.
  - fix: Return the same loading placeholder Layout uses while loading is true, before the if (user) redirect check.
  - area: apps/web/src/pages/Login.tsx
- [ ] **F194** [medium/bug] Login card is a fixed 360px with no page padding — it overflows on small phones
  - The card is w-90 (360px) inside flex min-h-screen items-center justify-center with no padding and no max-w-full. On a 360px viewport it touches both edges; below that, or at any browser zoom level, it overflows and the page scrolls sideways. Testers on this team open the tool from the phones they are borrowing, so a narrow viewport is the normal case.

- [ ] **F195** [medium/ux] Server-unreachable shows as "Failed to fetch"
  - Login renders err.message raw. - [ ] **F196** [low/polish] Full-page bare "loading…" on every reload, and the tab title never changes
  - While /auth/me resolves, the entire app is a single lowercase grey "loading…" at the top-left of a blank page — the same string Devices and other pages use. ### Product gaps a QA team will hit

- [ ] **F198** [high/gap] A tester can return a device to nobody — no receipt confirmation, unlike handover
  - ReturnRequestHandler sets holderId = null and status = 'available' the moment the requester clicks Return, and only the requester ever sees that button, so return is always self-declared. Handover deliberately refuses to move a device without the current holder confirming — the Handovers copy says "the system never pretends a phone moved when it didn't" — and return breaks that same promise. The device shows available and immediately bookable while it is still in a backpack, and the accessory check is self-graded.
  - fix: Mirror the handover contract: Return moves the request to a `returning` state with the device still held, and the desk (or the next approved requester) confirms receipt with the accessory checklist, which is what flips it to available. Keep single-step return behind an approval_mode-style flag.
  - area: apps/api/src/requests/requests.commands.ts
- [ ] **F199** [medium/gap] Data goes in by Excel but never comes out — no export anywhere
  - ImportService reads .xlsx and exceljs is already a dependency, but there is no export route on devices, requests, the idle report or the audit log. A telecom QA lead will be asked for an inventory spreadsheet — a stock count, an insurance list, a budget request, the eventual migration to Azercell infra — and the only answer is copy-paste from the browser or direct DB access.
  - fix: Add GET /devices/export.xlsx emitting the same column names the importer accepts, so export → edit → re-import round-trips, plus export buttons on the idle report and the audit log. Stream, don't buffer.
  - area: apps/api/src/reports/reports.controller.ts (agreement: 3)
- [ ] **F200** [medium/gap] No waitlist — a tester who needs a booked device has to keep checking manually
  - RangeCalendar makes conflicting days unpickable, which is right, but the dead end is unhandled: a tester who needs the one iPhone 15 Pro this week can only pick a gap after the current booking or come back tomorrow. Nothing captures that demand, so managers never learn which devices are over-subscribed. Early returns are common — the return flow frees a device the instant it is checked in — so the notify-when-free case fires often enough to matter. GOALS.md:66 lists it as post-v1.
  - fix: Add "Notify me when free" on DeviceDetail and next to a blocked range, storing a waitlist row; on return, cancel or rejection, notify waiters in order through the existing notify/outbox path with a deep link that pre-opens the request modal. The table doubles as demand data for the purchase report.
  - area: apps/web/src/components/RangeCalendar.tsx
- [ ] **F201** [low/gap] No repeat bookings for regression cycles
  - Each request covers exactly one contiguous range. QA work is cyclical — a regression pass every sprint, a weekly release check — so the same tester books the same device on the same weekday repeatedly, filing an identical request and reason each time, each queuing separately for approval. Lowest-value item here, but cheap once the overlap constraint is doing the hard work.
  - fix: Add an optional "Repeat weekly until <date>" control creating N linked requests sharing a group id, approved or rejected together, skipping colliding occurrences with a visible note rather than failing the whole batch.
  - area: apps/web/src/components/RequestModal.tsx
- [ ] **F202** [medium/bug] Historical requests render as blank rows once their device is deleted
  - Device soft-delete is only blocked while a request is open, so retiring an old phone leaves finished requests pointing at a deleted device. TypeORM filters that relation out of the joins, pub() falls back to { id: r.deviceId } with no brand or model, and RequestTable renders "undefined undefined". The same null relation reaching loadRequest would throw a TypeError on request.device.brand and return a 500 instead of a real message.
  - fix: Load the device withDeleted in the requests query and in loadRequest, and have pub() return brand/model plus a deleted: true marker the UI can show struck-through. Keep the null branch as a loud fallback, not the normal path.
  - area: apps/api/src/requests/requests.controller.ts

## Praise (keep these qualities)

- The booking rule is enforced by Postgres, not by application code. The GiST exclusion constraint in migrations/1724800000000-requests.ts makes overlapping approved/active/overdue bookings physically impossible for one device, and the handlers map 23P01 back to a readable 409. This is the right instinct — the invariant that matters most is the one an app bug cannot violate — and it is why the only double-booking hole left is a boundary case (the overdue window) rather than a race.
- Audit coverage is genuinely complete and correctly transactional. Every state-changing handler across all 31 mutating endpoints writes its audit row inside the same withTransaction as the change, so there is no window where a mutation lands without its record. Requests even audit resolved names (device, requester) rather than raw ids in some paths — the pattern the rest should follow.
- The Excel importer's two-phase dry-run/commit contract is unusually honest for an internal tool: row-level errors with reasons, a count of what will land, and nothing written until the user confirms. It treats a partial failure as data to show rather than something to swallow, and the error messages are written for the person holding the spreadsheet.
- The handover step refuses to pretend. ConfirmHandoverHandler distinguishes holderConfirms from deskConfirms and rejects anyone else with a message that says which case applies — the app will not mark a phone as moved because a form was submitted. That is exactly the right model for physical custody, and the Handovers page copy explains it plainly.
- The CQRS-lite layer is consistently applied: commands carry an explicit Actor, AppDbContext hands every handler the same typed repositories inside one transaction, and the request state machine is a single declarative transition table rather than scattered ifs. Adding a state or a command is a small, obvious change — which is why most of the findings above are localized fixes rather than restructuring.
- The design reference in mockups/index.html is real, detailed, and mostly honoured, and the product thinking behind approval_mode, soft-delete-everywhere and the pluggable IdentityProvider shows someone read GOALS.md rather than guessing. Where the app drifts from the mockup (the overdue banner, the repair count, the focus ring, the Holds column), the mockup turns out to be right — which makes those regressions cheap to spot and cheap to fix.
